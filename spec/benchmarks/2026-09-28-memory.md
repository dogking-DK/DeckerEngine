## 工作负载与指标口径

87 个矩阵场景：三组 size/alignment（32/8、256/64、4096/256）、1/2/4/32 线程，
同线程回收覆盖 heap、heap PMR、arena、local pool、shared pool；环形相邻线程回收覆盖 heap/PMR/shared pool。
另外一个管线场景通过 token/cache 绑定生产线程，以 scratch vector 和 local ObjectPool 生成 256 个 uint64，
发布 owning vector/shared 结果，由消费线程校验并销毁；weak 控制块的延迟释放也受检查。
每个进程合计 88 场景；9 次独立运行共 792 次场景执行。

- 吞吐：每秒完成且验证过的逻辑分配请求数，管线为每秒结果数。矩阵每次进程有 7,593,984 个测量请求，管线 512 个测量结果。
- 计时包含分配、首尾载荷写入/校验、释放、batch 时钟和末端同步。跨线程每 batch 有两次 barrier；arena 每 batch 整体 rewind。
  因生命周期和同步不同，不能把差值直接解释为分配器或 remote free 单次成本。
- 创建资源/线程、预热、统计排序、trim/析构在计时外。管线 latency 为每次交接墙钟；矩阵 latency 为各 worker batch 的分布。
  每次先算 p50/p95/p99，再对三次运行取中位数；不是合并三次样本后求分位数。耗时比为该模式耗时中位数 / OFF 耗时中位数。
- heap peak 是资源记录的 backing 请求峰值（含预热），retained 是清理前的空闲保留量；不是进程 RSS 或 mimalloc 实际保留页。
  local logical peak 的和不是同时峰值，不能与 backing 相加。管线 heap peak 是两个域各自峰值之和，CSV 标为 `sum_domain_peaks`；其 retained 仅指局部缓存。
- pool 选项为 max_blocks_per_chunk=32、largest_required_pool_block=4096；arena 使用既有默认 chunk/保留策略。
  peak 在三次间取最大，retained 取中位数；STL pool 的上游块数允许随运行变化。
- 顺序轮换为 OFF/CPU/Memory、CPU/Memory/OFF、Memory/OFF/CPU。采集器与被测进程同机运行，profiling 开销包含同步、传输和本地采集器竞争。

## 正确性与采集验收

9 次运行全部通过；三配置/三次重复的同场景 checksum 相同，所有场景最终 live allocations 和 backing bytes 均为 0。
管线逐轮确认局部缓存保留量稳定，worker 退出后局部 backing 归零；最后的 weak 使 close 返回 busy，释放后 close 成功。
CPU CSV 精确核对 87 个 Case、504,288 个 Batch、1 个 Pipeline、544 个 Import，其他内部 zone 也必须闭合且带源码位置。

CPU-only 每次均无内存事件/曲线。Memory 每次的 jobs/assets 事件数均与独立 heap 累计计数一致，
所有 alloc/free 配对且无存活对象，异线程释放不少于工作负载推导的下界。
12 条 scratch/local/shared pool 曲线全部读回；当前用量最终归零，sampled-peak 保留峰值。
trace 内 backing 分配数轻微变化来自标准库 pool 的运行期布局/线程调度，以各次独立计数核对，不硬编码精确块数。

## 结论与限制

在 256/64、32 线程这个固定批次负载中，local pool/arena 的复用减少了上游申请，但分别保留约 259 KiB/2 MiB backing；
heap/PMR 在 batch 释放后保留量为零。shared pool 支持跨线程回收，当前实现的竞争及标准池开销使本负载吞吐较低。
这些数据描述本实现的生命周期取舍，不能据此断言某种策略适合所有引擎对象。

Memory/OFF 耗时比在同线程 32-worker arena 达到 75.710，显著高于 CPU-only 的 1.166。
这与 scratch checkpoint/rewind 的高频采样经过进程级互斥聚合路径相符（见
[record_scratch_sample](../../engine/foundation/profiling/src/Memory.cpp)）；本轮未做因果隔离实验，
后续若优化此负载，应单独测量采样频率/锁竞争，不能仅把开销归因于分配器。

最终 OFF 的最宽三次吞吐范围出现在 PMR 同线程、1 worker、32 bytes：约 7.67–23.35 M requests/s，相差 3.04 倍。
管线 CPU/OFF 的 0.639 也伴随明显范围差异，不视为 profiling 提速。当前报告提供初始观测和可重跑入口，
不支持精细排名、稳定的微小回归阈值或真实导入性能结论。

这些负载只写块的首尾，不能代表完整内容填充、缓存带宽、复杂对象构造或真实引擎帧时间。
正式采集前的短轮次试跑显示较大波动，因此将 64/8 测量/预热轮提高到 512/32；
原始试跑 `20260928-095808-cbe026c7` 保留。`20260928-100008-05415094` 的完整结果也保留，
最终在一处计时外异常安全修正后使用交付源码重新采集本报告，不按最快结果挑选运行。
即使增加轮数，本机短用例仍受调度和频率影响。应比较完整 min/max 范围，不能将小比例差异或耗时比小于 1 解释为确定收益。
未运行真实资产导入器/Jobs、GPU、其他平台、sanitizer、硬件固定频率/亲和性或长期稳态测试；未做 Tracy GUI 视觉验收。
本次完成测量设施及基线，未更改生产分配策略、默认 chunk/pool 参数或自动装配 Runtime 内存上下文。
