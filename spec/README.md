## 文件和元数据

设计文件使用稳定模块名：`spec/design/<module>.md`；复杂模块可分为
`graphics-device.md`、`graphics-graph.md` 等。修改现有模块时更新原设计，
避免为同一模块建立互相矛盾的现行设计。

开发文件使用 `spec/development/NNNN-short-title.md`，从 `0001` 起全局递增，
按数字排序；编号不复用、不因归档而重排。新任务取目录中最大编号加一，
已有任务继续更新原记录。多人同时工作时落盘前检查冲突，超过 9999 后统一扩展位宽。

两类文档均使用 YAML 元数据：

- `created_at`：创建时间，创建后不改写。
- `updated_at`：最后实质修改时间，每次实质更新时刷新。
- 时间格式：ISO 8601，带时区，例如 `2026-09-22T09:00:00+08:00`。
- `status`：设计使用 `draft / accepted / superseded`；开发使用
  `in-progress / completed / blocked`。accepted 表示当前采用的方案，
  不代表新增人工审批步骤。
- 设计含 `module`；开发含 `id` 和 `design_refs`（相对该文件的设计链接）。
- 正文保留可点击的相关设计、开发记录和代码路径。

## 命令文档

可调用命令的使用说明放在 `spec/commands/`，按功能分组，目录入口为 README.md。
每条命令说明用途、参数/必填项/默认值、返回值、前置条件、guard、副作用/撤销范围、
常见错误和调用示例；公共类型与协议规则在入口集中说明。
参考页记录 created_at、updated_at，更新时保留创建时间；不分配开发日志编号。
新增、修改或删除命令时同步对应参考页和目录。以 commands.list/commands.describe
核对实际注册与 schema，并运行受影响的示例；业务语义同时对照模块设计与实现。
模块设计保存设计理由，skill 保存开发方法；具体命令定义不复制到 skill 中。

## 开发记录粒度

新增模块、完整 Mx.y 小阶段或涉及接口、持久化协议、依赖和生命周期的重要变更，
使用独立编号记录。小型修改或补丁不要求逐次新建文档：

- 相关小改优先合并到已有模块/任务记录，同一记录可以覆盖多次修改；
  保留 created_at，更新 updated_at，并区分每次改动和实际验证结果。
- 简单、局部、无额外设计决策或交接信息的补丁可以不写开发日志，
  在提交说明和交付回复中说明变化与验证即可。

是否新增记录按实际复杂度和交接价值判断，不按修改次数或文件数量机械分配编号。
已有设计仍须与实现保持一致；重要语义变化不能因为代码量小而省略设计说明。

## 每次开发的执行顺序

先定位 Roadmap 的 Mx.y 小阶段，说明本次范围和独立验收条件。
默认的“下一步开发”只推进一个满足前置的小阶段；用户明确要求多个阶段时按其范围执行。
完成后更新小阶段状态、证据与下一项，全部子阶段通过后才关闭父里程碑。

1. 读取根目录 `AGENTS.md`、架构总览、相关模块设计、该模块最近的开发记录。
2. 开发新模块前复制设计模板，填写目标、边界、依赖方向、接口/数据、
   生命周期、错误处理、验证计划和未决问题。修改已有模块时先更新受影响设计。
   未涉及的内容写“本次不涉及”及原因，不堆积空章节。
3. 设计足以指导当前范围后，按上述粒度选择新建、合并或免写开发记录。
   新建记录时分配编号、设置 `in-progress` 并加入索引；合并时继续已有记录。
   遵循用户已授权的任务范围直接开发。
4. 需要留档的任务，每完成一项有意义的变更或发现影响方案的问题，更新开发记录：
   改了哪些文件、为何修改、实际行为、依赖/命令变化、验证结果。
   实现偏离原设计时先修订设计，再继续实现。
5. 结束前核对设计与代码一致，在记录或交付说明中写明实际运行的检查及结果，
   明确未运行的检查、限制与下一步；只在本次范围完成后标记 completed。
   使用开发记录时同步索引状态和 `updated_at`，保留最初 `created_at`。

只读分析不要求新建开发记录。纯文档修订直接维护对应文档及修改时间，
若它属于正在留档的开发任务则同步该任务记录。文档不替代验证，也不把计划写成已实现结果。
